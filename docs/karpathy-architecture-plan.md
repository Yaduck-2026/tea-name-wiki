## 對本專案的修正

先前規劃以 JSON 文章供網站建置，尚未實作原始來源保存、Markdown 知識主檔及跨頁整合流程。因此上一份完整性報告只表示舊規則內部一致，不代表已符合這次指定的模式。

**調整決策提案：Markdown Wiki 成為內容的唯一主檔；網頁是它的公開閱讀介面。** JSON 僅可留作分類設定、工具產物或遷移備份，不再與 Markdown 並行手動維護兩份知識。

## 建議目錄

```text
tea-name-wiki/
  AGENTS.md                 # 匯入、問答、檢查、寫作及網頁規則
  raw/                      # 匯入時保存的來源版本，不由 AI 改寫
    articles/               # 可保存的文章／PDF／使用者資料
    social/                 # 可保存的貼文擷取與來源資訊
    references/             # 僅有連結時的紀錄，明示不是全文
  wiki/                     # LLM 持續維護的 Markdown
    index.md                # 分類索引與每頁一句摘要
    log.md                  # 依時間追加操作紀錄
    overview.md             # 茶知識總覽
    sources/                # 每份來源的摘要與支持／衝突說法
    origins/                # 台灣產地
    cultivars/              # 品種
    tea-types/              # 茶類
    specialties/            # 特色製法／茶款
    styles/                 # 製作風格
    brewing/                # 沖泡
    tea-names/              # 完整茶名拆解
    syntheses/              # 跨來源比較、近期話題及問答成果
  templates/                # Markdown 模板
  docs/                     # 指南、進度、遷移與討論紀錄
  site/                     # 網站共用版型
  scripts/                  # 本地檢查與建置
  dist/                     # 產生的公開網頁
```

資料夾名稱是本專案提案，不宣稱原文指定了這套命名。

## TeaWIKI 的操作約定提案

### 1. 搜尋與匯入

你說「搜尋這週茶知識」時，才啟動已確認的近七天搜尋規則。找到合格資料後保存可合法保存的來源版本、記錄帳號與連結，再逐份整合：檢查既有條目、修訂相關頁、補關聯、更新總覽和索引、追加 log。不是只在文章清單末尾新增一篇。

來源版本一旦匯入便不改寫；後來更新的原文另存新版本。全文不可取得或不宜保存時，只建連結紀錄並標示限制，不將 AI 摘要冒充原文。不自動把 raw 發布到網站。

### 2. 問答

你問茶知識問題時，AI 先讀 Wiki 索引，再讀相關頁，以可追溯引用回答。不夠的部分直接說明；沒有你的搜尋指示，不自行對外補查。你說「把這個比較整理進 Wiki」時，再將結果存為比較頁並補關聯與紀錄。

問答由協作對話中的 AI 執行，網站首版仍不加入即時聊天，也不新增模型金鑰需求。

### 3. 健康檢查

你要求檢查 Wiki 時，分開檢查檔案與知識：工具找失效內部連結、重複 ID、缺來源和孤立頁；AI 閱讀內容找矛盾、概念重複、資料缺口及過期說法。來源不同的結論並列出處，不只憑 AI 自信判定。檢查不自動搜尋新來源。

### 4. 網站閱讀與作業呈現

沿用「茶名有解」名稱、雜誌風、完整茶名拆解、六大分類、白話口語與舉例。網站從可公開的 Wiki Markdown 建置，保留文末帳號／來源及跨頁連結；研究原件不因 GitHub 公開而一併外流。

Obsidian 可作本地閱讀工具，但不列為必須安裝的依賴；課堂要求的公開網站仍保留。

## 遷移順序與驗收

1. 保留現有 8 份內容及 8 筆來源，先修訂 AGENTS.md 與 Markdown 模板，不刪舊資料。
2. 將既有條目轉為 Wiki，保留原來源與查閱日期；既有連結清單不等於已保存原件，缺少原件的來源明示限制。
3. 用一份實際可讀、可取得的來源示範完整匯入：至少更新來源摘要、相關知識頁、index 與 log；若有其他受影響頁也同步修改，不刻意湊頁數。
4. 示範一次有引用的 Wiki 問答及一次健康檢查，留下實際操作紀錄。
5. 再做 Markdown 到公開網站的建置、操作驗證與 GitHub 發布。
