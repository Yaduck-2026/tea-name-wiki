# 茶名有解｜AI 開發與內容維護規則

> 架構修正中：使用者最新指定採用 Karpathy LLM Wiki 模式。先閱讀 [架構調整方案](docs/karpathy-architecture-plan.md) 與最新討論紀錄。下方 JSON 主檔方案為舊版，待確認後遷移至 raw／Markdown Wiki／schema 架構；目前不得繼續依舊方案製作網站。茶主題、六大分類、白話舉例、查證與手動觸發要求仍有效。

本文件適用於 `tea-name-wiki/` 及其子目錄。AI 開始工作前，先閱讀本文件、`README.md`、`docs/content-guide.md` 與 `docs/progress.md`。使用者的新指示優先；有衝突時先記錄具體差異，不默默改變已確認範圍。

專案規則以本文件為準；欄位細節見內容指南，模板必須與兩者一致。製作階段、實際可用指令與驗證結果以 progress 和 package.json（建立後）為準。規則變更時同步相關指南與模板，不讓歷史進度覆蓋目前規則。

## 1. 專案目的與首版範圍

建立繁體中文茶知識 LLM Wiki，面向初學者，以台灣茶為重點，提供六大茶類入門。透過完整茶名拆解，讓讀者看懂各詞代表的產地、品種、製作風格及採收季節，再連到相關知識。

LLM 用於協助研究、整理、查證及維護內容；首版不加入即時 AI 問答，不需要模型 API 金鑰。

已確認首版：

- 首頁以「完整茶名拆解＋六大分類」為主，另設近一週話題專區。
- 六大分類索引，每類至少 1 篇基礎知識條目；「茶類」先以 1 篇介紹六大茶類。
- 至少 1 個完整茶名拆解範例。
- 近一週話題研究：資料足夠時提供 1 篇查證統整；不足時如實提供期間與限制說明。
- 關於本站、查證方法、搜尋、交叉連結及手機版閱讀。
- 完整專案最終上傳 GitHub，網站公開可瀏覽。

不要自行加入商城、會員、評論或模型聊天。使用者已明確指定手動觸發：只有使用者要求「搜尋」「更新 TeaWIKI」或明確授權來源研究時，才進行新一輪查找、查證及內容更新；不設定背景排程，不在使用者只是開站或討論排版時自動搜尋。每次討論後更新決策紀錄的約定維持有效。

區分兩種搜尋：網站搜尋框只查已建立的站內內容，不連外或觸發 AI；使用者在協作對話中要求查找茶資料，才是研究更新任務。檢查規則、調整排版與建置網站可以讀取既有檔案，不因此展開新研究；若任務確實缺少新資料，先在討論文件記錄並請使用者指定是否搜尋。

## 2. 技術與目錄約定

採用靜態網站：結構化 JSON 內容＋共用 HTML/CSS/JavaScript 版型，以 Node.js 20 以上建置，輸出至 `dist/`；預設使用內建能力，避免不必要的框架及外部依賴。僅執行當時已建立的指令，不得把未實作功能說成已可使用。

```text
tea-name-wiki/
  AGENTS.md                  # AI 的規則入口
  README.md                  # 專案說明、使用方式與階段狀態
  config/categories.json     # 六大主分類的唯一資料來源
  content/
    wiki/                    # 長期知識條目 JSON
    tea-names/               # 完整茶名拆解 JSON
    digests/                 # 有固定觀察期間的話題統整 JSON
  sources/registry.json      # 來源目錄；內容以 sourceIds 引用
  research/                  # 搜尋、熱度觀察與查證紀錄 Markdown
  templates/                 # 三種內容模板與研究模板
  docs/                      # 內容指南、進度與延伸指令
  assets/images/             # 可合法公開的圖片／插圖
  assets/image-credits.json  # 圖片出處、授權與替代文字
```

後續實作時才新增 `scripts/`、`site/` 與 `dist/`。`site/` 放共用版型、樣式和前端程式；`scripts/` 放建置、驗證及預覽工具。變更生成網頁時應修改內容或版型，再建置，避免只手改 `dist/`。

- 檔名與穩定 ID 使用小寫英文加連字號，例如 `qingxin-oolong.json`。
- `id` 必須等於不含副檔名的檔名，在三種內容中全站唯一；發布後避免改動。
- 研究檔命名：`YYYY-MM-DD-topic.md`，日期採台灣時間。
- 不建立同義重複條目；別名放 `aliases`，較大議題以交叉連結組合。
- 內部關聯存 ID，不手寫部署網址；未實作網址映射前不捏造連結。
- 網頁資源須支援專案子路徑部署，避免寫死網域或根目錄絕對路徑。
- 後續網址固定為首頁 `index.html`、分類 `categories/<categoryId>/index.html`、知識 `wiki/<id>/index.html`、茶名 `tea-names/<id>/index.html`、話題 `digests/<id>/index.html`、關於 `about/index.html`。內部連結由同一個路徑函式產生並計算相對路徑，分類與搜尋沿用它。
- `dist/` 只包含公開頁面及所需資產，不整個複製研究資料夾或草稿。about 頁須說明規則並提供可讀的 AGENTS.md 入口；授權公布的規則檔可另行複製。

## 3. 六大分類（固定順序）

| ID | 顯示名稱 |
| --- | --- |
| origins | 台灣產地 |
| cultivars | 品種 |
| tea-types | 茶類 |
| specialties | 特色製法／茶款 |
| styles | 製作風格 |
| brewing | 沖泡 |

由 `config/categories.json` 產生分類導覽。每篇知識條目指定 1 個主分類，可選擇其他既有分類作補充。採收季節屬茶名欄位／標籤，不自行增加第七個主分類。

## 4. 內容格式與發布條件

複製 `templates/` 的對應 JSON，依 `docs/content-guide.md` 填寫。

### 寫作語氣（使用者指定）

- 使用白話、口語化的繁體中文，像陪初學者看茶單；句子簡短自然，不堆砌術語或寫成學術論文。
- 專有名詞初次出現時，先說它在講什麼，再給貼近日常買茶、看包裝或泡茶的例子。
- 優先使用「意思是……」「例如你看到……」「可以先把它想成……」解釋；比喻需說明界線，不能取代正式定義或證據。
- 正確保留專有名詞，讓讀者之後能查找原文；不能為了好懂把品種、茶類、氧化、焙火等不同概念說成同一件事。
- 每篇知識條目至少有一個具體例子；茶名拆解的每個關鍵詞附白話說明。例子是教學情境時明示為假設，不捏造真實商品、經歷或來源。
- 來源支持知識結論；自行設計的理解練習要能辨識為本站的教學安排。

### 資料與發布狀態

- `kind` 為 `wiki`、`tea-name` 或 `digest`；不得混用模板欄位。
- 共用欄位包含 `id`、`title`、`summary`、`status`、`updated`、`relatedIds`、`sourceIds`。
- `status` 僅為 `draft`、`review`、`published`。模板及待查證內容留在 draft；review 表示待複核，均不得公開為正式知識。
- `published` 僅代表內容已完成本專案的查證與檢查、可納入建置，不代表人工背書、商品鑑定或網站已部署。網站是否公開，以實際部署結果為準。
- 複核由執行本次任務的 AI 逐點核對來源、欄位、例子與適用範圍，並在研究紀錄留下結果；使用者可以要求再審閱，未要求時不新增逐篇批准關卡。結構檢查通過不等於完成事實查證。
- `updated` 使用實際修改日 `YYYY-MM-DD`。不得為了顯得新穎只改日期。
- 段落以純文字儲存，來源引用另存 `sourceIds`；不插入任意 HTML。
- 知識與話題的每個段落組使用 section，包含 `heading`、`paragraphs`、`bullets`、`sourceIds`。
- `published` 內容不得有未填佔位字、空白必填欄位或尚待查證的核心結論。每個非空的事實 section 及已確認茶名詞語都要有可核對的來源引用。
- published 條目的 `relatedIds` 只能指向其他 published 條目，且不可重複或自我引用；draft／review 可暫時指向其他草稿，但目標 ID 仍需存在。未來條目的想法先寫 research，不用虛構 ID 佔位。
- 發布頁文末顯示來源目錄；section 的引用與文末來源需可對應。`sourceIds` 包含該文所有引用，不能出現不存在的來源 ID。
- 註明限制、條件、品牌觀點及不確定處；茶品介紹不寫成醫療療效宣稱。
- 修改既有 Wiki 時保留穩定 ID，依實際變更更新日期，並在研究紀錄及 progress 記錄主要修正理由。新的七天觀察建立新的 digest ID；舊觀察保留原區間，錯誤修正需留更正紀錄，不覆寫成新一期。

## 5. 完整茶名拆解

使用者提供的版型範例：

`杉林溪龍鳳峽・青心烏龍・清香型・冬茶`

| 詞語 | 角色 |
| --- | --- |
| 杉林溪龍鳳峽 | 產地 |
| 青心烏龍 | 品種 |
| 清香型 | 製作風格 |
| 冬茶 | 採收季節 |

此例是需求範例，不代表已驗證存在這款商品。研究後可作有來源的組合示例，但需說明示例性質；不暗示特定茶廠正在販售。

- 呈現順序：完整茶名 → 原順序拆詞及角色 → 白話翻譯 → 關聯知識 → 文末來源。
- `terms` 每項含原詞 `text`、角色 `role`、說明 `explanation`、`categoryId`、`entryId`、`verification` 及 `sourceIds`。
- 角色可為產地、品種、茶類、特色製法／茶款、製作風格、採收季節或其他；無對應主分類時 `categoryId` 為 null。
- `verification` 為 `pending` 或 `verified`；公開範例的每個詞須 verified。`entryId` 可 null，不能連到不存在或未公開的內容。
- verified 僅表示該詞在示例中的角色與解釋已具備來源；不表示這款商品、產地履歷或批次品質經檢驗。`illustrative` 與 `source-based` 的示例性質必須在頁面上明示，不能只存在 JSON 裡。
- 名稱沒有寫出的資訊，不為湊齊分類而補入。不能由單一詞語推測茶類、實際製程或沖泡數值。
- 白話翻譯只整合已確認資訊，不增加未有來源的香氣、海拔、品質或功效。

## 6. 近一週社群選題

本節僅在使用者手動要求搜尋／內容更新時執行。定期排程不是本專案需求，不能因舊文章變舊就自行搜尋或重寫。

每次執行研究時取得實際時間，以 `Asia/Taipei` 往回 7 天，保存帶 `+08:00` 的開始、結束與查閱時間。以原貼文發布時間篩選，不用搜尋引擎收錄時間代替。

同批研究以記錄的 end 作唯一截止，start 為 end 減 7 天，納入區間為 start ≤ 發布時間 ≤ end。end 在完成這批搜尋時定稿，定稿後新增查找屬下一批；沒有確切時分的日期，只有在整日都落於區間內時才納入，邊界日無法確認時間者排除。

1. 查找公開可讀的 Threads、Instagram 茶知識內容；無指定帳號。優先核對茶廠官方身分，也可記錄其他相關公開討論，註明帳號性質。
2. 在 `research/` 記錄查詢詞、平台、讀取結果、時間、原貼文、帳號、可見互動數及缺失資料。讀不到、日期不明或超出期間者記錄排除原因。
3. 依知識問題分組，去除轉貼與同帳號重複內容；不把促銷、抽獎互動當知識討論。
4. 依可辨識的知識留言／回覆及獨立帳號數比較；按讚、分享只作補充。平台分開記錄，缺失數值為 null，不能填 0。整篇貼文的留言總數不等於已確認的知識相關留言數。
5. 若可比數據不足，不強行排名；說明選題理由及限制。對外稱「本次可取得樣本中的近期討論焦點」，不宣稱全平台最熱門。
6. 提取可查證說法，再查官方、研究或專業原始資料；查證來源不受近 7 天限制。社群重複出現不等於正確。
7. 正文分開寫「社群在討論什麼」「查證結果」「限制或不同說法」，連到長期 Wiki；保留當時觀察期間，不隨日期自動改成這週。

選題紀錄要列出實際找到的候選知識問題及選中理由；資料可比時才並列比較，不用未定義的綜合熱度分數。相同觀察範圍且資料完整時可按知識相關回覆數比較，再參考不同發文帳號數；指標互有高低則說明差異，不硬選唯一冠軍。只有一則合格貼文時可做該貼文的知識查證，但不能稱為多帳號共同焦點。

**資料足夠的最低判準**：有可讀原貼文、可確認在期間內的時間、可對應知識說法及可核對查證來源，才能寫實質話題統整；這不保證足以排名。熱度資料不足時另註明不能比較熱度。完全沒有合格貼文時，僅發布「觀察限制說明」，列出實際查詢及限制，不編造話題、帳號或數字。

`digest` 的 `evidenceLevel` 為 `verified-topic` 或 `insufficient-data`。不足資料的 published 紀錄可沒有來源 ID，但必須有真實研究檔、查詢紀錄、觀察期間與限制，且不能包含無來源的茶知識結論。

## 7. 來源與圖片

- 優先核對使用者指定的官方來源：[食農教育資訊整合平臺「逗陣來識茶」](https://fae.moa.gov.tw/theme_data.php?id=50&sub_theme=knowledge&theme=topics)、[農業部茶及飲料作物改良場](https://www.tbrs.gov.tw/index.php)，並可補充農業知識入口網及其他可核對的原始研究／專業資料。社群用於發現問題，官方與研究資料用於查證，不能混淆其角色。
- 引用支持知識點的具體文章或教材，不只列機關首頁；原站無法讀取時，可用已確認出處的官方刊載版本，保存實際讀取網址並註明限制。不要把舊資料當作當週消息。
- `sources/registry.json` 集中維護來源。來源類型為 `social`、`official`、`research` 或 `professional`。
- 共用欄位見 `templates/source.json`；實際發布引用須有真實標題、作者／機構、原始網址、查閱日期、支持的說法及讀取狀態。日期取不到用 null 並說明，不猜測。
- social 額外填平台、帳號名稱、帳號識別名稱、官方身分查核依據。無法確認身分要明記，不擅稱官方。
- 帳號首頁不能代替原貼文；知識來源要連到支持說法的具體頁面。
- 話題文章的文末來源分為「社群討論來源」與「知識查證來源」，社群欄顯示平台、帳號及原貼文連結；長期基礎條目不必硬附無關社群來源。無合格貼文的觀察限制說明可無社群來源，但必須明示未取得。
- 品牌對自家茶款的描述註明品牌與適用範圍；來源衝突時留下差異，不擅自合成確定結論。
- 搜尋摘要只作線索，未讀取原文不得標為已查證。閱讀受限者保持待查，不繞過登入或權限。
- readable 表示在 accessedAt 當時已讀取，不保證連結永遠有效。本地結構檢查及建置不自動連外查證；使用者要求複查時才重查。新寫內容若缺來源，維持 draft／review；舊引用失效則留查閱日期與限制，若已確認核心結論有誤，先修正或暫撤該條目，再修復指向它的公開連結。
- 自行摘要，不整篇搬運；研究紀錄也不保存非必要的大量原文或個人資訊。
- 圖片放 `assets/images/`，出處與授權記錄於 `assets/image-credits.json`；無明確使用依據的社群照片不重用。
- 原創／生成插圖需標為示意，不能當特定產地、真實商品或實作結果的證據。圖片有具體 alt，純裝飾圖採空 alt。

## 8. 視覺與可用性

- 茶文化雜誌風：米白、深茶綠、茶褐，較大的編輯式標題、適當留白及茶主題圖像。
- 色彩、字級、間距用共用 CSS 變數管理；新頁沿用共用版型，不逐頁建立不同設計。
- 六大分類保持一致順序；茶名拆詞在手機上也按原順序閱讀，不靠顏色單獨區分角色。
- 文字對比清晰、內文行距舒適、連結與按鈕可辨識；鍵盤可操作、焦點可見，表單有標籤。
- 搜尋及分類有無結果提示，文章可直接開啟與分享，來源連結可點擊。

## 9. AI 工作流程與驗收

1. 先確認目前階段及使用者授權範圍，讀規則與相關既有內容，避免另建重複資料。
2. 依任務選模板。研究先存紀錄，再存來源，最後寫條目；不先產出結論再補假來源。
3. 更新相關內容、來源及交叉連結；對新增功能先檢查是否需要修改本文件和指南。
